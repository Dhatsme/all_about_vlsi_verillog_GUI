VeeR EL2 Lab

A real, open-source RISC-V core (VeeR EL2, from CHIPS Alliance) and its real UVM testbench, simulated with Verilator on our server. Run programs on the CPU, then open the UVM testbench, change it, and rerun it.

Checking server…

What happens when you press Run

The server loads a compiled RISC-V program into the core's memory as program.hex, then runs a Verilator model of the full VeeR EL2 core. The program writes text to a memory-mapped console address and finally reports TEST_PASSED or TEST_FAILED.

The Instruction trace shows every instruction the CPU retired, with register updates — the same log verification engineers compare against a reference model.

Pick a program and press Run.

The DCCM UVM testbench

This testbench verifies VeeR's data memory (DCCM) on its own. It has every standard UVM piece: a sequence item, sequences, a sequencer, a driver, a monitor, an agent, a scoreboard and a test. Pick a file on the left to read it. Edit anything, then press Run — the server rebuilds only what changed and runs the test.

Runs are queued one at a time. Most edits rebuild and run in under a minute. An edit that uses a class in a new way (for example a new type_id::create call) makes Verilator regenerate much of the UVM library, which can take several minutes — leave the page open while it builds.

Exercise: a test that passes but checks nothing

Run the test unchanged. It prints DCCM TEST PASSED with 0 errors. Now count how often the scoreboard prints READ DATA Match or READ DATA Mismatch in the log.

Then open dccm_monitor.sv: the monitor creates one transaction object and reuses it for every bus cycle, and wr_en is set but never cleared. Fix it so the scoreboard really checks reads. What does the scoreboard report now?
